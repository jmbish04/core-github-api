# Backlog Data Model and Plan Revision Tracking

This document outlines the proposed schema changes and API/Frontend updates to implement the robust many-to-many relationship structure for backlog items (Epics, Phases, Sprints, Stories, Tasks) and proper tracking of implementation plans and revisions generated by AI agents.

## User Review Required

> [!WARNING]
> **Data Model Shift:** The current structure assumes simple 1:M parent/child relationships (e.g. `stories` point to `epics`). Moving to an explicit M:M mapping table structure allows infinite flexibility (e.g., tasks belonging to tasks, stories belonging to multiple epics) but will require heavier API logic to query tree hierarchies using joins. 
> 
> Please review the schema structure below to ensure this fully aligns with your architectural goals.

## Proposed Changes

### 1. Plan Revisions Schema

We will create a new tracking structure for implementation plans/revisions that hook directly into the AI orchestrator lifecycle.

#### [NEW] `plan_revisions.ts` (file:///Volumes/Projects/workers/core-github-api/src/backend/src/db/schemas/projects/plan_revisions.ts)
- `id`: UUID (Primary Key)
- `planId`: Unique identifier that persists across revisions (UUID)
- `julesSessionId`: Links to the AI execution session
- `repoOwner` / `repoName`: GitHub coordinates (FK optional but good for context)
- `revisionNumber`: Integer (1, 2, 3...)
- `isFinal`: Boolean
- `humanFeedback`: Text (captures HITL commentary)
- Timestamps

### 2. Backlog Item Schemas (Adding Plan Tracing)

Every primitive within the backlog (Phases, Sprints, Epics, Stories, Tasks) must reference the exact implementation plan revision that spawned it.

#### [MODIFY] `phases.ts` 
- Populate standard fields: `id`, `repoId`, `title`, `description`, `status`, `startDate`, `endDate`, `planRevisionId` (FK to plan_revisions).

#### [MODIFY] `sprints.ts` 
- Populate standard fields: `id`, `repoId`, `title`, `description`, `status`, `startDate`, `endDate`, `planRevisionId`.

#### [MODIFY] `epics.ts`, `stories.ts`, `tasks.ts`
- Inject the `planRevisionId` tracking column into existing definitions.
- *Note:* We will leave the legacy `parentId` as an optional bridge column but primarily rely on the new M:M tables below.

### 3. Many-to-Many Mapping Tables

To satisfy the infinite depth M:M linking requests, we will generate mapping tables capturing every connection point explicitly.

#### [NEW] `mappings.ts` (file:///Volumes/Projects/workers/core-github-api/src/backend/src/db/schemas/projects/backlog/mappings.ts)
Table definitions:
- `phase_sprints_map` (phaseId, sprintId)
- `phase_epics_map` (phaseId, epicId)
- `sprint_epics_map` (sprintId, epicId)
- `epic_epics_map` (parentEpicId, childEpicId) 
- `epic_stories_map` (epicId, storyId)
- `epic_tasks_map` (epicId, taskId)
- `story_stories_map` (parentStoryId, childStoryId)
- `story_tasks_map` (storyId, taskId)
- `task_tasks_map` (parentTaskId, childTaskId)

#### [MODIFY] `index.ts` 
- Add relations blocks for deep nesting queries referencing the M:M structure (using `many()` on both sides of the junction tables).

### 4. API and Frontend Integration

#### [NEW/MODIFY] API Routes
- Expand `src/backend/src/routes/api/projects/backlog/*` to support fetching plans and their linked nested M:M trees.
- Add an endpoint for HITL plan approval that accepts `humanFeedback`, bumps `revisionNumber`, and emits the generated Backlog items cleanly.

#### [MODIFY] Frontend UI
- Add/update React Query bindings for `TrackerReportsViewBeta.tsx` and `VelocityPage.tsx` or create a new dedicated `BacklogTree` view component to visualize the M:M nesting and the plan version timeline.
